# Build Plan

Checklist, worked top-to-bottom. Each item is exactly one file with a single responsibility — `stage`/`apply` should be able to touch one checklist item without needing to also change any other file. Phases are ordered by dependency (later phases consume earlier ones).

Mission: implement the financial optimization product comparison pipeline described in `overview.md` on top of the existing FastAPI + Vite/React skeleton.

## Phase 9: Coupons
Best-active-coupon lookup by retailer, backed by CouponAPI.org's periodic full CSV feed sync (confirmed via a real sample: `full_5647_20260912175001.csv`, 661 rows — filename pattern `full_<id>_<timestamp>.csv` is a scheduled snapshot dump, not a live per-request API). Architecture: an ingest step loads the feed into a local Postgres table; lookups query that table, never CouponAPI.org directly. Frontend display trigger/UI is out of scope for this phase — backend lookup capability only.

Feed columns (confirmed from the real sample): offer_id, title, description, label, code, featured, source, deeplink, affiliate_link, cashback_link, url, image_url, brand_logo, type, store, merchant_home_page, categories, standard_categories, start_date, end_date, status, primary_location, locations, language, rating. Notably: `status` is always empty (unusable), there is no `verified_at`-equivalent field, and `rating` is a small int (0-2 observed).

Open question, not blocking: how daily feed delivery gets automated (authenticated download URL vs. manual re-upload) is unconfirmed. Ingestion is built against a local CSV path; automating retrieval is follow-up work.

Its actual use is now uncertain — no live call needs it; may end up used only if CouponAPI.org exposes an authenticated feed-download URL. Kept, not removed, pending that answer.
- [x] `backend/app/coupons/models.py` — revised: dropped `verified_at` (no feed equivalent), added `start_date: datetime | None` and `rating: int` to `CouponOffer`, matching the real feed's available ranking signals.

Parses the CSV feed (stdlib `csv.DictReader`) from a local file path, upserts each row into a `coupon_offers` Postgres table via `db.py`'s pool, keyed by `offer_id` so re-running the loader on a newer feed is idempotent (replace-on-conflict, not insert-only). ## Phase 14: Browser Extension
A real Manifest V3 browser extension — not the `ExtensionPanel.tsx` marketing-page mockup, which is a normal SPA screen rendered via `App.tsx`'s own state machine with a fake browser-chrome frame drawn around it, fed from the app's own already-fetched search results. This phase builds the thing that actually runs on a third-party retailer's page.

Locked decisions, via Q&A: **site scope is generic/any-site** (no per-domain selector table — contradicts the scope, and breaks silently on redesigns anyway); **popup auto-searches immediately** on an add-to-cart-style click (no manual search-bar step); **detection is structured-data-first** (JSON-LD `Product`/OpenGraph), falling back to generic DOM heuristics, never per-site CSS selectors; **backend integration reuses `POST /api/search`** verbatim (detected title as `query`, same shape as today's Exact Product mode) rather than a new endpoint; **the trigger is the click itself, not arrival at a `/cart`/`/checkout` URL** — resolved via a hole found in review: content scripts run in an isolated JS world, so patching `history.pushState` from `content.ts` does not observe the page's *own* calls to it (a known Chrome-extension gotcha), which would have made SPA-navigation-based detection unreliable. Click-based detection sidesteps that entirely — DOM click events are dispatched on the shared DOM and are observable by a content script's own listener regardless of isolated worlds. This also means no `chrome.webNavigation` permission is needed at all. Trade-off, accepted: a one-page "Buy Now"-only checkout with no visible add-to-cart-style click goes undetected — out of scope for this phase.

Known gaps, carried forward as documented limitations rather than silently solved or hidden (same practice as `routes/search.py`'s `EXACT_PRODUCT_MAX_WORDS` note):
- **Savings-accuracy gap**: `/api/search` re-resolves its own target via SerpAPI's top hit for the detected title — it does not take the page's real price as input. The "you could keep $X" figure can diverge from what the page actually showed if SerpAPI's top match for that title isn't the exact listing the user was looking at. Fixing this means teaching `/api/search` to accept an optional real-target override; out of scope for this phase.
- **No React in the injected popup**: bundling React into a content script running on arbitrary third-party pages is real bundle-size/CSP/perf cost for a hackathon-scope feature. The popup is hand-written HTML/CSS/vanilla JS mirroring `ExtensionPanel.tsx`'s visual structure, not a port of the component. No bundled image assets either (brand mark is inline SVG/text in the template), so no `web_accessible_resources` entry is needed in `manifest.json`.
- **Click-target text-matching is still a heuristic**, not a certainty — text-matching click targets ("add to cart"/"add to bag"/"buy now"/"checkout"/"place order") and their ancestors up a few levels (button text often lives on a child `<span>`, not the clicked element itself). Will have false positives/negatives across the long tail of retail sites; no way around that at this scope.
- **CORS may not even be the operative fix.** A background service worker with `host_permissions` covering a given origin can generally fetch it without the server needing to send CORS headers at all — that's a documented extension-specific exemption, different from an ordinary page's CORS rules. The `main.py` item below is kept as defense-in-depth (and for any future non-extension cross-origin caller), but whether it's actually load-bearing for the extension itself needs verifying once this is built end-to-end, not assumed.
- **No icon assets exist** — only `frontend/public/favicon.svg`. Chrome extensions need raster PNGs (16/48/128px); someone needs to export those. Not fabricated here.
- **No domain yet** (`deploy/README.md` — both boxes are bare IP, no TLS), so the extension's API base has to point at that IP:port, not a real hostname, until one exists.
- **`extension/package.json` isn't covered by `instructions.md`'s Dependency Rule** (which names `backend/pyproject.toml`/`uv.lock` and `frontend/package.json`/`package-lock.json` only) — flagging that its bundler dependency (`esbuild`) needs a `branchDep.md` row and the rule's file list arguably needs to grow to cover it; confirm with the user before the `extension/package.json` item lands.
- **`content_scripts.matches: ["<all_urls>"]` is unavoidable given the generic-scope decision**, and triggers Chrome's strongest install-time warning ("read and change all your data on all websites"). Fine for a hackathon demo/unpacked install; would need real user-trust framing before any public Web Store listing. `host_permissions` itself is kept narrow — just the backend API's own origin, not `<all_urls>` — since that permission is about background-script fetch access, not content-script injection scope, and least-privilege costs nothing here.
- **No automated verification wired up for the new TypeScript files** — `tsc`/eslint should still be run manually against `extension/` after each item in this phase lands, the same way `ruff`/`mypy`/`pytest` run after every backend apply. Only *packaging as a CI release artifact* is deferred below, not basic typecheck/lint.
